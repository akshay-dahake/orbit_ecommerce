*
diff between pathvariable and RequestParam

| Feature      | `@PathVariable`   | `@RequestParam`      |
| ------------ | ----------------- | -------------------- |
| Location     | URL path          | Query string         |
| Purpose      | Identify resource | Filter/modify data   |
| Mandatory    | Usually yes       | Optional             |
| REST Meaning | Resource identity | Query options        |
| Example URL  | `/users/5`        | `/users?active=true` |


@PathVariable is used to extract values from the URI path to identify a resource
Commonly used in RESTful APIs
ex-
GET /users/101

@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) { }

@RequestParam is used to extract query parameters for filtering or modifying the response.
Used for search, sorting, pagination
ex-
GET /users?active=true&page=1
@GetMapping("/users")
public List<User> getUsers(
    @RequestParam boolean active,
    @RequestParam(required = false) Integer page) { }



When to use which (experienced insight)

Use @PathVariable when:
Identifying a specific resource
URL represents a noun
Example: /orders/{orderId}

Use @RequestParam when:
Applying filters, sorting, pagination
Parameters are optional or combinational
Example: /orders?status=OPEN&sort=date

What is idempotent?
If you send the same request multiple times, the result remains the same.

PUT → Idempotent ✅
PUT /users/10
Body: { "name": "Akshay" }

Send it 1 time or 10 times →
User name is Akshay
✔ Safe for retries

POST → Not idempotent ❌
POST /users
Body: { "name": "Akshay" }

Send it twice →
❌ Two users may be created
First Request
👉 Creates a user:
User ID: 101
🧾 Second Same Request
👉 Creates another user:
User ID: 102

PUT vs PATCH (HTTP Methods)

🔹 PUT
Definition:
PUT is used to replace the entire resource with the data provided.

🔹 PATCH
Definition:
PATCH is used to partially update a resource.

Key Difference (one line – remember this)
PUT = full replacement
PATCH = partial modification

Example (very important)
Existing resource
{
  "id": 10,
  "name": "Akshay",
  "email": "akshay@gmail.com",
  "age": 25
}

PUT example
PUT /users/10
{
  "name": "Akshay D",
  "email": "akshayd@gmail.com"
}

🔴 Result after PUT:

{
  "id": 10,
  "name": "Akshay D",
  "email": "akshayd@gmail.com",
  "age": null
}
➡ Missing fields may be removed or reset

PATCH example
PATCH /users/10
{
  "email": "akshayd@gmail.com"
}

🟢 Result after PATCH:

{
  "id": 10,
  "name": "Akshay",
  "email": "akshayd@gmail.com",
  "age": 25
}
➡ Only the given field is changed

diff type of status code

1️⃣ 1xx – Informational

Request received, processing continues.

Code	Meaning			Usage
100	Continue	        Client should continue request
101	Switching Protocols	WebSocket upgrade

👉 Rarely used in REST APIs.

2️⃣ 2xx – Success

Request was successfully received and processed.

Code		Meaning			When to use in Spring Boot
200 OK	        Success			GET, PUT
201 Created	Resource created	POST
202 Accepted	Request accepted	Async processing
204 No Content	Success, no body	DELETE

return ResponseEntity.ok(data);            // 200
return ResponseEntity.status(201).body(x); // 201

3️⃣ 3xx – Redirection

Client must take additional action.

Code	Meaning			Usage
301	Moved Permanently	URL changed
302	Found			Temporary redirect
304	Not Modified		Caching

👉 Rare in REST APIs (mostly web apps).

4️⃣ 4xx – Client Error

Problem with client request.

Code		Meaning	 				Spring Boot Usage
400 Bad Request	Invalid input			Validation failure
401 Unauthorized ,Not authenticated		Missing/invalid token
403 Forbidden	Not allowed			No permission , not authorized to particularr api
404 Not Found	Resource not found		Wrong URL / ID
405 Method Not Allowed	,Wrong HTTP method	POST on GET endpoint
409 Conflict	Resource conflict		Duplicate data
415 Unsupported Media Type,Wrong Content-Type	JSON expected and we are sending xml or other
422 Unprocessable Entity,Validation error	Semantic issue

return ResponseEntity.badRequest().build(); // 400

5️⃣ 5xx – Server Error

Problem on the server side.

Code	Meaning				When it happens
500 Internal Server Error		Generic server error,Unhandled exception
502 Bad Gateway	Invalid upstream	API gateway issue
503 Service Unavailable			Down/overloaded	Maintenance
504 Gateway Timeout			Timeout	Slow upstream


Summary
Class	Meaning

        registry.addMapping("/api/**")

                .allowedMethods("GET", "POST", "PUT", "DELETE")

what is magAge there 
maxAge property controls how long the browser can cache the results of a CORS preflight request.

1️⃣ What is a Preflight Request?

For non-simple requests (like PUT, DELETE, or requests with custom headers), 
the browser sends an OPTIONS request first.
This is called a CORS preflight request.
The server responds with allowed methods, headers, and origins.

2️⃣ maxAge Purpose

maxAge tells the browser:
“You can reuse this preflight response for the next X seconds without sending another OPTIONS request.”
Type: long (seconds)
Default: 1800 (30 minutes) in Spring (if not set)

Browser won’t send OPTIONS for /api/** for 1 hour
Reduces network traffic
Improves performance

How can you upload a file in spring and spring boot application
-->
spring provided a data type called Multipart

-->Steps
1.Include spring-boot-starter-web
2.Configure multipart.max-file-size if needed
3.Use @RequestParam("file") MultipartFile file in controller
4.Save file locally, database, or cloud
5.Return ResponseEntity with status and info


1.Dependencies ->
Spring Boot automatically includes multipart support via spring-boot-starter-web. For file storage, 
you may optionally use spring-boot-starter-thymeleaf for forms or commons-io.

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>


2.Configure Multipart (optional)-->
By default, Spring Boot supports multipart uploads. 
You can configure limits in application.properties or application.yml:

spring.servlet.multipart.max-file-size=10MB       // means Maximum size of a single uploaded file will 10MB , If any one file exceeds 10 MB, Spring will reject the request
spring.servlet.multipart.max-request-size=20MB    //   Maximum total size of the entire HTTP request  Includes: All files,Form fields,Multipart metadata
                                                          If the combined request size exceeds 20 MB, the request is rejected


3.Controller – Single File Upload
@RestController
@RequestMapping("/api/files")
public class FileController {

    @PostMapping("/upload")
    public ResponseEntity<String> uploadFile(@RequestParam("file") MultipartFile file) {

        if (file.isEmpty()) {
            return ResponseEntity.badRequest().body("File is empty");
        }

        try {
            // Save file to local folder (example)
            Path path = Paths.get("uploads/" + file.getOriginalFilename());
            Files.createDirectories(path.getParent());
            Files.write(path, file.getBytes());

            return ResponseEntity.ok("File uploaded successfully: " + file.getOriginalFilename());
        } catch (IOException e) {
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                    .body("Error uploading file");
        }
    }
}

Notes:
@RequestParam("file") binds the uploaded file
MultipartFile has methods like:
getOriginalFilename()
getBytes()
transferTo(File dest)


Controller – Multiple File Uploads
@PostMapping("/uploadMultiple")
public ResponseEntity<String> uploadMultiple(@RequestParam("files") MultipartFile[] files) {

    StringBuilder uploadedFiles = new StringBuilder();

    for (MultipartFile file : files) {
        if (!file.isEmpty()) {
            try {
                Path path = Paths.get("uploads/" + file.getOriginalFilename());
                Files.createDirectories(path.getParent());
                file.transferTo(path.toFile());
                uploadedFiles.append(file.getOriginalFilename()).append(", ");
            } catch (IOException e) {
                return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                        .body("Error uploading files");
            }
        }
    }

    return ResponseEntity.ok("Uploaded files: " + uploadedFiles);
}



Large File Uploads -->

Use spring.servlet.multipart.max-file-size and max-request-size to increase limits.

Consider streaming files with InputStream instead of getBytes() to avoid memory issues:

InputStream is = file.getInputStream();
// save stream to disk or cloud storage

example->
@PostMapping("/upload")
public void upload(@RequestParam MultipartFile file) throws IOException {
    byte[] data = file.getBytes(); // entire file in heap
    Files.write(Paths.get("/tmp/" + file.getOriginalFilename()), data);
}

Problems
    High memory usage
    Fails with large files
    Not safe for concurrent uploads

✅ Recommended approach (streaming with InputStream)

@PostMapping("/upload")
public void upload(@RequestParam MultipartFile file) throws IOException {

    Path target = Paths.get("/tmp/" + file.getOriginalFilename());

    try (InputStream inputStream = file.getInputStream()) {
        Files.copy(inputStream, target, StandardCopyOption.REPLACE_EXISTING);
    }
}

Why this is better
    Reads file chunk by chunk
    Memory usage stays low
    Scales well with large files


With MultipartFile, using getBytes() loads the entire file into heap memory, which doesn’t scale. 
Streaming with InputStream processes data incrementally, making the application memory-efficient and safe for large or concurrent uploads.”

Storing Files Options-->

Local disk – simple, for small apps
Database (BLOB) – if you need atomic storage
Cloud storage (AWS S3, GCP, Azure) – scalable, production-ready

How do you maintain versioning for REST api
-->
versioning is useful for backward compatibilty

1.Versioning in URL Path (Most Common)
Pattern: /api/v1/resource

Controller Example
@RestController
@RequestMapping("/api/v1/users")
public class UserV1Controller {

    @GetMapping("/{id}")
    public UserDto getUserV1(@PathVariable Long id) {
        return service.getUserV1(id);
    }
}

@RestController
@RequestMapping("/api/v2/users")
public class UserV2Controller {

    @GetMapping("/{id}")
    public UserDtoV2 getUserV2(@PathVariable Long id) {
        return service.getUserV2(id);
    }
}

Pros:
Simple to implement
Easy for clients to understand

Cons:
Can create duplicate code if versions differ slightly

2.Versioning via Request Parameter

Pattern: /api/users?id=1&version=2

Controller Example
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping
    public Object getUser(@RequestParam Long id,
                          @RequestParam(required = false, defaultValue = "1") int version) {

        if (version == 1) {
            return service.getUserV1(id);
        } else {
            return service.getUserV2(id);
        }
    }
}

Pros:
Single endpoint
Easy to switch versions

Cons:
URL can get messy with multiple query parameters
Versioning logic inside controller

3.Versioning via HTTP Header

Pattern: Custom header X-API-VERSION: 2

Controller Example
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping(value = "/{id}", headers = "X-API-VERSION=1")
    public UserDto getUserV1(@PathVariable Long id) {
        return service.getUserV1(id);
    }

    @GetMapping(value = "/{id}", headers = "X-API-VERSION=2")
    public UserDtoV2 getUserV2(@PathVariable Long id) {
        return service.getUserV2(id);
    }
}

Pros:
Keeps URLs clean
Flexible for advanced clients

Cons:
Harder for browser testing (headers required)
Less visible for casual users

4️⃣ Versioning via Media Type / Accept Header (Content Negotiation)

Pattern: Accept: application/vnd.company.app-v2+json

Controller Example
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping(value = "/{id}", produces = "application/vnd.company.app-v1+json")
    public UserDto getUserV1(@PathVariable Long id) {
        return service.getUserV1(id);
    }

    @GetMapping(value = "/{id}", produces = "application/vnd.company.app-v2+json")
    public UserDtoV2 getUserV2(@PathVariable Long id) {
        return service.getUserV2(id);
    }
}

Pros:
Fully RESTful
Allows content negotiation
Clean URLs

Cons:
More complex for clients
Harder to test without custom tools

-->Best Practices for API Versioning
Start with URL versioning (/v1/) — easiest and most visible.
Avoid breaking changes — deprecate old versions gradually.
Document versions clearly in Swagger/OpenAPI.
Separate controllers/services per version to reduce risk of breaking older APIs.
Consider backward compatibility — e.g., V2 adds optional fields rather than removing fields.
Use semantic versioning if needed (v1.0, v1.1) for fine-grained changes.

-->Spring Boot Versioning Summary Table

| Approach          | URL Example                           | Pros              | Cons                       |
| ----------------- | ------------------------------------- | ----------------- | -------------------------- |
| URL Path          | `/api/v1/users`                       | Simple, visible   | Duplicate controllers      |
| Request Parameter | `/api/users?version=2`                | Single endpoint   | Messy URLs                 |
| Custom Header     | `X-API-VERSION: 2`                    | Clean URLs        | Harder for browser testing |
| Accept Header     | `Accept: application/vnd.app-v2+json` | RESTful, flexible | Complex for clients        |

Sometimes endpoints are internal but still need to exist. You can hide them from Swagger/OpenAPI.

@RestController
@RequestMapping("/api/internal")
@Hidden                        // Swagger 3 annotation
public class InternalController {

    @GetMapping("/metrics")
    public String getMetrics() {
        return "Internal metrics";
    }
}

@Hidden is from io.swagger.v3.oas.annotations.Hidden
Endpoint works, but doesn’t show in Swagger UI


2.Do Not Map Certain Controllers Publicly

Only include internal controllers in internal profiles.
Use @Profile("internal") so that the bean/controller is not loaded in production/external profile.

@RestController
@RequestMapping("/api/internal")
@Profile("internal")
public class InternalController {

    @GetMapping("/metrics")
    public String getMetrics() {
        return "Internal metrics";
    }
}

Only available when Spring Boot runs with --spring.profiles.active=internal

3.Use Spring Security to Restrict Access (Recommended)

The most robust way is authorization. You keep the endpoint in your code, 
but only allow internal roles or requests from specific clients.

Example: Restrict to ADMIN role
@RestController
@RequestMapping("/api/internal")
public class InternalController {

    @GetMapping("/metrics")
    @PreAuthorize("hasRole('ADMIN')")
    public String getMetrics() {
        return "Internal metrics";
    }
}

Requires spring-boot-starter-security
Configure roles and authentication
External users without ADMIN cannot access it (403 Forbidden)
